# Silent VPN для Keenetic — 1.0.171

Отдельный порт клиента для KeeneticOS + Entware. В архиве собственный агент, встроенная веб-панель Silent, наш VK/WDTT-транспорт `spass` и WireGuard userspace. Сервер использует прежний API, `device_type=pc`, имя устройства `Keenetic <hostname>`. Старые клиенты и сервер не требуют изменений.

Статус: экспериментальная сборка, прошедшая локальные проверки. Реальная установка/работа на Keenetic пока не подтверждены. «Универсальная» означает варианты CPU с проверкой требований, а не гарантию для каждой модели/прошивки.

Исходники: `footballpredictions/Silent`, ветка `keenetic`. Пакеты и обновления публикуются отдельно: https://github.com/silentvpn3/silentvpn3.github.io/releases/tag/v1.0.171. Метадата OTA — `keenetic.arches` в https://silentvpn3.github.io/releases.json; пакеты OpenWrt для Keenetic не подходят.

## Архитектуры

Универсальный `dist/silent-vpn-keenetic-1.0.171.tar.gz` содержит aarch64, ARMv7, ARMv5, MIPS little endian, MIPS big endian, x86_64 и i386. Есть меньшие отдельные архивы для каждого CPU. MIPS выбирается по ELF byte order `/bin/sh`, не только по `uname`; ARMv6 использует совместимый ARMv5 вариант. Статические бинарники: CGO отключён, musl/glibc не нужны.

## Требования

- KeeneticOS с настроенным Entware на USB EXT4 или поддерживаемом внутреннем NAND-разделе. На моделях без такой среды клиент не устанавливается.
- Для общего адреса панели требуется штатный HTTP proxy KeeneticOS (`ndmc`, команды domain static / preserve-host / x-real-ip / security-level private, KeeneticOS 3.5+). Штатный HTTP-порт роутера должен быть 80; установщик не меняет порт или доступ к настройкам самого роутера.
- Linux 3.2+, EPOLL/FUTEX; `/dev/net/tun` и рабочая поддержка TUN ядром. При необходимости установите компонент OpenVPN/IPsec через KeeneticOS; создание device node само по себе не добавляет драйвер.
- Root shell Entware, `ip-full`, `ipset`, `iptables`/`ip6tables`, поддержка MARK, DNAT, MASQUERADE, conntrack и ipset ядром, включённый IPv4 forwarding. Установщик проверяет часть требований до запуска; остальные проверяются при подключении с очисткой частичных правил.
- Свободное место под два выбранных бинарника и конфигурацию: ориентир 45 МБ плюс распаковка/backup. Для универсального архива и распаковки желательно от 300 МБ свободного места на накопителе. Не используйте /opt/tmp без проверки: он может ссылаться на RAM /tmp. Универсальный архив распаковывайте на накопитель Entware; для малого хранилища используйте архив выбранной архитектуры. Свободную RAM и скорость необходимо проверить на устройстве, userspace WG и VK-транспорт требуют CPU/RAM.
- Основной частный IPv4 LAN bridge, по умолчанию `br0` (fallback `br-lan`). Только его клиенты проходят через VPN. Для другого bridge задайте `SVK_LAN_INTERFACE`; гостевые сети отдельно не захватываются.
- Собственные таблица 20513, приоритеты policy rules 51/52, mark `0x53000000/0xff000000`, имена интерфейса `svkeen`, цепочек `SVK_*`, ipset `svk_direct`/`svk_vpn` должны быть свободны. Не устанавливайте поверх конфликтующих Entware VPN/перехватчиков без проверки.

## Установка

Скопируйте выбранный архив на накопитель роутера и выполните в Entware shell:

```sh
mkdir -p /opt/share/silent-keenetic-install
cd /opt/share/silent-keenetic-install
# Скопируйте архив в эту папку перед распаковкой.
tar -xzf silent-vpn-keenetic-1.0.171.tar.gz
cd silent-vpn-keenetic-1.0.171
sh install.sh
```

Установщик ставит зависимости через Entware OPKG. Если они уже подготовлены: `sh install.sh --no-deps`. Другой основной bridge: `SVK_LAN_INTERFACE=br0 sh install.sh`.

Основной вход одинаков с OpenWrt: `http://<LAN-IP>.silent.vpn`, например `http://192.168.1.1.silent.vpn`. Открывается та же панель с формой аккаунта Silent VPN, без дополнительного браузерного логина admin. Дизайн, экраны и операции панели совпадают с OpenWrt; различается адаптер системы. Используйте кабель или Wi-Fi выбранного LAN и DNS самого роутера.

Агент настраивает только собственный DNS-host и HTTP proxy `silent-vpn-panel` через NDM. Прокси доступен лишь из private LAN, сохраняет Host и передаёт настоящий IP клиента. Прямой IP роутера продолжает открывать его штатные настройки. После отключения VPN адрес панели остаётся доступен; при активном VPN встроенный DNS отвечает на это имя локально. При остановке/удалении удаляются только принадлежащие Silent записи; существующие и изменённые вручную чужие настройки сохраняются. Новая конфигурация проверяется до выдачи сигнала готовности, частичная установка откатывается.

Резервный старый вход `http://<LAN-IP>:8787` сохранён для совместимости, с прежним admin/случайным паролем. Он не требуется для основного входа. Старые KeeneticOS, переписывающие Origin в прокси, требуют современного браузера с Sec-Fetch-Site; неоднозначные запросы отклоняются. HTTP используется внутри доверенного LAN.

Настройки и токены: `/opt/etc/silent-keenetic/config.json`, права 0600. Не пересылайте файл целиком — в нём секреты. Здесь можно изменить LAN/порт/пароль, затем перезапустить сервис. При обновлении конфигурация сохраняется. При ручной установке предыдущий runtime/config копируются в `/opt/var/backups/silent-keenetic-*`; при OTA резервная копия временная и удаляется до перезапуска клиента.

```sh
/opt/etc/init.d/S99silent-keenetic status
/opt/etc/init.d/S99silent-keenetic stop
/opt/etc/init.d/S99silent-keenetic start
/opt/lib/silent-keenetic/silent-keenetic --check
```

## Маршрутизация, DNS и восстановление

Транспорт идёт через WAN; WG разговаривает с ним только на `127.0.0.1:9000`. Клиент сначала получает свежий `wg-turn.conf`, дожидается WG handshake и доступности шлюза, проверяет `/api/vpn/connect`, затем включает захват LAN. Панель обращается к API через туннель только при наличии его адреса и маршрута; при сетевой ошибке/5xx использует все четыре резервные соты и публичный API. Отказы 4xx, включая 401/402/403 и ответы без JSON, не обходятся переключением API. Health проверяет именно туннель, поэтому доступность API через WAN не маскирует поломку VPN. Main default и настройки WAN не меняются; в main добавляется только маршрут `/32` до шлюза туннеля. Чужие VPN, DHCP и системный DNS не перезапускаются.

DNS прокси на LAN:15353 принимает перенаправленные LAN UDP/TCP53. Обычные запросы идут через туннель, выбранные российские домены — через WAN DNS Яндекса `77.88.8.8/77.88.8.1`; их A-ответы добавляются в частный ipset до ответа клиенту. Политика direct/vpn берётся из общего `/api/vpn/routing-policy` каждые 300 секунд и сохраняется как последний исправный кеш; при первом запуске без сервера используются оба списка из актуального OpenWrt. VPN-исключения имеют приоритет над direct, включая совпавшие IP CDN. При изменении revision пересоздаются только свои learned sets, без перезапуска DNS/NDM/системных служб. Learned IP сохраняются до отключения, без таймера, который конфликтовал бы с DNS-кешем. Общий IP CDN может расширить обход; DoH/DoT/жёстко заданные IP не дают достоверного доменного исключения.

VPN пока IPv4: AAAA подавляются, IPv6 forwarding выбранного LAN блокируется на время подключения, чтобы не обходить VPN. IPv6 к самому роутеру не блокируется. После отключения собственные правила удаляются.

NDM netfilter hook восстанавливает только свои цепочки изменённой таблицы, без reconnect в общей очереди NDM. Supervisor очищает собственные маршруты/DNS-правила после падения агента и запускает его повторно. Каждые 20 секунд восстанавливаются свои маршруты, rules и исчезнувшие sets/цепочки; learned direct/vpn IP восстанавливаются из памяти агента. Запуск supervisor и OTA не требует nohup и переживает закрытие запускающей SSH-сессии. Последнее успешно подключённое состояние восстанавливается после перезагрузки; явное отключение убирает автоподключение. Три последовательных сбоя health (~60 с) отключают туннель и возвращают обычный интернет; автоматическое повторное подключение после этих health-сбоев не выполняется. Это поведение fail-open, строгого kill switch нет.

## Обновление через панель

Панель синхронизирована с OpenWrt от 2026-10-14: версия берётся из агента, меню закрывается кнопкой X, стрелка возвращает в меню, вложенный магазин — на предыдущий экран. Сохранены исправления входа/повторного открытия панели и обновления списка сессий. Кнопка обновления находится только на главном экране и появляется при публикации более новой сборки именно Keenetic для выбранного CPU.

OTA читает только `keenetic.arches.<CPU>` из `https://silentvpn3.github.io/releases.json`. Контракт записи: `platform=keenetic`, `arch`, `version`, `size`, `unpacked_size`, `sha256`, `build_id`. Скачивание — фиксированный GitHub Release файл `silent-vpn-keenetic-VERSION-CPU.tar.gz`; URL из произвольной метадаты не исполняется. Пакеты OpenWrt и универсальный Keenetic архив для OTA не принимаются. Локальная проверка доступна через GET `/cgi-bin/silent-api/update-check`, статус — GET `/update-status`, запуск — POST `/update-start` с теми же LAN/Basic/Origin проверками и активным аккаунтом. Параллельные изменения клиента во время обновления блокируются.

Скачивание и потоковые проверки SHA256, CPU/ELF, ARCH/VERSION/PACKAGE.json, состава/размеров/безопасности архива выполняются при работающем VPN. Только после проверки останавливается собственный сервис, повторно проверяется свободная RAM, выполняются распаковка/временный rollback/установка. Конфигурация, аккаунт, пароль панели и намерение автоподключения сохраняются. Payload и rollback удаляются до старта сервиса, включая сценарии ошибки; неудачная установка восстанавливает предыдущие runtime файлы. Не используется экспериментальный fallback backup на flash, откатанный сегодня в OpenWrt. При недостатке памяти обновление отказывается от установки и запускает прежний клиент.

Архивы публикуются в GitHub Releases и семи слотах Keenetic серверной админки. OTA сначала проверяет сервер через туннель/резервные API, затем публичный Pages releases.json. Для первой установки и обновления старого порта без OTA используйте ручной архив. Общая команда на лендинге определяет OpenWrt или Keenetic; на Keenetic она запускается из заранее настроенного Entware. Первоначальная установка Entware остаётся отдельной подготовкой роутера.

## Что проверить на реальном Keenetic

1. Запуск CPU-варианта, `--check`, доступность панели по кабелю/Wi-Fi.
2. Handshake, внешний IP клиента LAN, достижимость интерфейса управления Keenetic во время VPN.
3. DNS UDP/TCP, RU direct, YouTube/Telegram через VPN; IPv6 не уходит напрямую.
4. Отключение, перезагрузка, падение агента, восстановление NDM правил при WAN-событиях.
5. FastNAT/PPE, уже открытые соединения, другие политики Keenetic/Entware и скорость.

Ускорение FastNAT/PPE может обходить policy/netfilter для части потоков. Клиент не выключает ускорение глобально и не сохраняет изменённую конфигурацию Keenetic. До реальных испытаний не обещайте захват всего трафика или конкретную скорость. Подробности и первичные источники, включая предоставленную тему 4PDA: [RESEARCH.md](RESEARCH.md).

## Удаление

```sh
sh /opt/lib/silent-keenetic/uninstall.sh
# При необходимости удалить также аккаунт/настройки с роутера:
sh /opt/lib/silent-keenetic/uninstall.sh --purge
```

Первый вариант сохраняет конфигурацию. Удаляются только пути и правила Silent Keenetic; зависимости Entware и чужие службы остаются.

## Сборка из проекта

```sh
python keenetic/scripts/build.py
# Один вариант:
python keenetic/scripts/build.py --target mipsel
```

Go 1.26.2+, исходники `pc/wdtt-go` рядом. Собственные зависимости агента закреплены в `agent/go.mod` и `go.sum`. Скрипт реально компилирует каждый вариант, проверяет ELF architecture/endianness, собирает отдельные/универсальный архивы и `dist/SHA256SUMS`, `manifest.json`. Публикация и установка на роутер — отдельные действия. Дизайн панели сохранён из нашего OpenWrt; исходный OpenWrt проект не изменяется.
