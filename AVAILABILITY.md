# Агент доступности: детекция блокировок DPI/ТСПУ

Отвечает на один вопрос: **видят ли клиенты из России наши серверы, а если нет — как именно
их заблокировали и что делать**. Работает фоном под лидером (один воркер), пробы только читают:
ничего не рестартит и не трогает живые peer'ы.

- Админка: **Улей → «Доступность и блокировки (DPI / ТСПУ)»**
- Если админка недоступна — тот же отчёт по SSH (раздел ниже)

## Что проверяет

| Точка наблюдения | Как | Зачем |
|---|---|---|
| Локально (с Улья) | TCP/TLS/HTTP/UDP-listen/DNS | отделить «сервис лежит» от «нас блокируют» |
| Российские ноды | `check-host.net` (`ru*.node`) | взгляд из-за ТСПУ — главный источник |
| Контроль вне РФ | `check-host.net` (мир) | если отказ виден везде — это не блокировка |
| Соты | `POST /v1/net-probe` на cell-agent | Улей ↔ сота, когда внешние ноды молчат |
| Клиенты | `POST /api/vpn/reachability-report` | стадия отказа (`dns`/`tcp`/`tls`/`handshake`/`tunnel_dead`), тип сети, оператор |

### Зачем клиентская телеметрия, если сервер недоступен

Она нужна не для полного блока — его видят российские ноды. Она закрывает то, чего внешние
пробы не видят вообще, и в этих случаях API как раз доступен:

- **UDP срезан** — `check-host` не умеет честно проверить наш UDP (wdtt и WG не отвечают на
 мусорный пакет), а у клиента TCP 443 живой и он спокойно шлёт `handshake`
- **DPI по отпечатку потока** — туннель встаёт и умирает, API работает: `tunnel_dead` с возрастом туннеля
- **Мобильные операторы** — ноды `check-host` стоят в датацентрах, реальность абонента МТС они не показывают

Когда прямой путь до Улья всё же закрыт, репорт доходит другими каналами:
путь `vpn/*` в белом списке публичного failover соты (`:9100`, другой IP и порт) —
сота проксирует его на Улей; плюс bootstrap-туннель по VK-хешу. Не дошло сразу —
клиент держит репорт в очереди и досылает с полем `age_sec` (сколько пролежал),
чтобы отказ попал в **своё** окно агрегации, а не в текущее. Репорты старше 48 ч отбрасываются.

Очередь клиентов: PC — `pc/src/renderer/reachabilityReporter.ts`,
Android — `android/.../vpn/ReachabilityReporter.kt`. Оба не привязаны к каналу туннеля
(в отличие от `hashFailureReporter`, где при основном VPN флаг `isTunnelApiActive()` всегда
false и очередь не выгружалась): просто пробуют POST, а маршрут tunnel → public → соты
выбирает общий слой API.

Каналы: `api_tcp`, `api_tls` (TLS с нашим SNI), `api_http`, `tls_no_sni`, `wdtt_udp`, `wg_udp`,
`agent_tcp`, `ping`, `dns`.

Цели — только Улей и активные соты, то есть путь VPN. Proxy-ноды сюда не входят: у них свой агент
`proxy_health_loop`, а их SOCKS-порт закрыт для Улья, и «недоступен локально» тут читалось бы
как ложная поломка сервиса.

## Что различает

Классификатор (`ai/availability_classifier.py`) сравнивает каналы между собой и выдаёт вывод
с доказательствами, уверенностью и **готовым решением**:

| Вывод | Ключевой признак |
|---|---|
`ip_blackhole` | все каналы молчат из РФ, локально живы, вне РФ доступны
`port_block` | один порт мёртв, другие порты того же IP живы
`udp_block` | UDP мёртв, TCP к тому же адресу проходит
`sni_block` | TCP открыт, TLS с нашим доменом не проходит, без SNI — проходит
`protocol_fingerprint` | туннель поднимается и умирает (клиентская телеметрия), порты живы
`dns_poisoning` | российские ноды резолвят домен мимо наших адресов
`rst_injection` | reset вместо таймаута, локально соединение живёт
`http_stub` | ответ приходит, но не наш (заглушка/чужой код)
`throttling` | потерь нет, но RTT из РФ втрое выше контрольного
`asn_partial` | часть операторов не видит, часть видит (**≥2** фейла нод; один timeout из 3 — шум check-host)
`mobile_shutdown` | отказы почти только с `network_type=mobile`, внешние пробы проходят
`route_loss` | ICMP unreachable вместо дропа
`service_down` | локальная проба тоже не прошла — не блокировка
`no_vantage` | внешние пробы не выполнились и клиентских данных нет

Справочник по каждому методу (как это делают, признаки, решения, команды) —
`ai/availability_knowledge.py`, в админке он открывается кнопкой «Справочник».

## Отчёт по SSH (если админка недоступна)

Модуль лежит внутри контейнера API, поэтому достаточно `docker exec`:

```bash
ssh root@<IP_УЛЬЯ>
cd /opt/silent-vpn/backend

# последний сохранённый отчёт — самое быстрое
docker exec backend-api-1 python -m ai.availability_cli

# проверить прямо сейчас (сетевые пробы, ~30–90 с)
docker exec backend-api-1 python -m ai.availability_cli --run

# история прогонов (только итоги)
docker exec backend-api-1 python -m ai.availability_cli --history 20

# что присылают клиенты за последний час
docker exec backend-api-1 python -m ai.availability_cli --clients --window 60

# справочник методов блокировок и решений
docker exec backend-api-1 python -m ai.availability_cli --knowledge

# машинный вывод — можно забрать себе
docker exec backend-api-1 python -m ai.availability_cli --json > /tmp/avail.json
```

Коды возврата: `0` — всё доступно, `1` — нет данных/отчёта, `2` — найдены проблемы.

Что читать в выводе: строку `ДОСТУПНОСТЬ SILENT VPN — …`, затем блок `НАЙДЕНО ПРОБЛЕМ` —
у каждой проблемы есть `Что происходит`, доказательства, **`Решение`** и готовые команды.
Ниже — таблица `УЗЛЫ И КАНАЛЫ`: где `локально ok`, а `из РФ 0/5` — там и блокировка.

Если контейнер не поднят, отчёт всё равно можно достать прямо из БД:

```bash
docker exec backend-db-1 psql -U silent -d silent_vpn -c \
  "select ts, status, summary from availability_reports order by ts desc limit 5;"
```

## Ресурсы: почему агент не грузит сервер

- Прогон раз в **30 минут**, между прогонами агент спит (минимум 5 минут, даже если настройку поставить ниже).
- Перед каждым прогоном смотрит нагрузку хоста: при **CPU ≥ 85 %** или **RAM ≥ 92 %** цикл **пропускается**. Диагностика не важнее работы VPN.
- Снаружи проверяются не все узлы, а первые `AVAILABILITY_MAX_EXTERNAL_TARGETS` (Улей всегда первый) и не больше `AVAILABILITY_MAX_EXTERNAL_CHECKS` запросов за цикл. Остальные узлы видны по локальным пробам и пробам со сот.
- Сессия БД открывается только на чтение целей и на запись отчёта — во время сетевых проб соединение из пула не занято.
- Хранение ограничено: 300 последних отчётов, клиентские репорты — 48 часов и не больше 20 000 строк.
- Локальные пробы — это несколько сокетов с таймаутом 6 с; внешние — ожидание ответа `check-host.net`, то есть сон, а не расчёт.

## Инциденты: почему журнал не забивается

Журнал «Инциденты» общий для всего Улья, поэтому агент пишет туда редко:

- только `critical` и `error`; деградация и «нет данных» остаются в отчёте;
- проблема должна подтвердиться **двумя циклами подряд** — одиночный таймаут молчит;
- о той же проблеме напоминаем не чаще **раза в 12 часов**;
- не больше **2 записей за цикл** (выводы отсортированы по важности, остальное — в отчёте);
- проблема ушла — сигнатура забывается, в следующий раз сообщим заново;
- **ручной** запуск (кнопка «Проверить сейчас» и `--run` по SSH) в журнал **не пишет** вообще;
- о собственной поломке агент сообщает только после 3 фейлов подряд и не чаще раза в 12 часов.

Логика вынесена в чистую функцию `plan_incidents` (`ai/availability_classifier.py`) и покрыта тестами,
так что «а не зафлудит ли» проверяется тестом, а не на проде.

## Настройки

`app/config.py` — дефолты, админка перезаписывает их в `app_settings`:

| Ключ | Дефолт | Смысл |
|---|---|---|
`AVAILABILITY_AGENT_ENABLED` | `True` | включён ли фоновый агент
`AVAILABILITY_AGENT_INTERVAL_SEC` | `1800` | период прогона (минимум 300)
`AVAILABILITY_EXTERNAL_ENABLED` | `True` | пускать ли пробы через `check-host.net`
`AVAILABILITY_RU_NODES` | `4` | сколько российских нод брать
`AVAILABILITY_WORLD_NODES` | `2` | контрольные ноды вне РФ
`AVAILABILITY_MAX_EXTERNAL_CHECKS` | `10` | бюджет внешних проверок за цикл
`AVAILABILITY_MAX_EXTERNAL_TARGETS` | `3` | сколько узлов проверяем снаружи (Улей первым)
`AVAILABILITY_CLIENT_WINDOW_MINUTES` | `30` | окно агрегации клиентских репортов
`AVAILABILITY_PEER_PROBE_ENABLED` | `True` | пробы со сот через cell-agent
`AVAILABILITY_LOCAL_TIMEOUT_SEC` | `6.0` | таймаут локальных проб
`AVAILABILITY_SKIP_IF_CPU_PERCENT` | `85` | при такой загрузке CPU цикл пропускается
`AVAILABILITY_SKIP_IF_MEM_PERCENT` | `92` | то же по RAM
`AVAILABILITY_INCIDENT_CONFIRM_CYCLES` | `2` | сколько циклов подряд подтверждают проблему
`AVAILABILITY_INCIDENT_RENOTIFY_HOURS` | `12` | окно тишины по той же проблеме
`AVAILABILITY_INCIDENT_MAX_PER_CYCLE` | `2` | максимум записей в журнал за цикл

Выключить агент, ничего не деплоя: снять галочку «Агент включён» в админке.
