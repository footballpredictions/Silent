# Скидка только на первую оплату

`PromoCode.first_payment_only` по умолчанию false; старые промокоды сохраняют прежнее поведение.
Административное создание `/api/admin/promo` принимает дополнительный boolean, список промокодов возвращает его.
Стартовая миграция добавляет совместимую колонку с DEFAULT FALSE в `promo_codes`.

Для нового кода ЧЕЧИЛ согласованы: 30%, все семь поддерживаемых тарифов, 10 000 применений,
срок год со времени создания. Зарегистрированный пользователь без completed-платежей также подходит.
При регистрации код сохраняется как pending; успешный `/payments/promo/check` для любого валидного промокода тоже
сохраняет его для следующего checkout. Не только информационное сообщение: preview/init считают фактическую цену.
Профиль отдаёт скидочные payment_previews даже без платной подписки. Обновлённые клиенты показывают на карточках
только свежую персональную quote.amount с непустым promo_code; после проверки кода обновляют профиль.
Глобальный каталог и цены других пользователей не меняются. Старые клиенты могут по-прежнему рисовать обычную цену;
итоговая сумма и подтверждение оплаты в любом случае считаются сервером.

Проверяются активность, срок, исчерпание, наличие любого completed-платежа. Trial/бонусы сами по себе не являются оплатой.
Просмотр, регистрация и проверка кода use_count не увеличивают. Успешное уведомление оплаты увеличивает его один раз,
под блокировкой строки промокода; повтор webhook защищён существующей идемпотентностью платежа.

Для first-payment-кодов checkout блокирует строки PromoCode и User, учитывает неоплаченные резервы в лимите,
а повторный запрос того же тарифа возвращает тот же счёт. Не выпускаются несколько скидочных счетов на один аккаунт.
Смена тарифа после резервирования счёта требует поддержки; ранее согласованные суммы/тарифы не переписываются.
Неоплаченный первый скидочный счёт остаётся payable, чтобы повторное открытие не требовало второго использования кода.
Приём уже выданного оплаченного счёта не отменяется задним числом: внешняя QuickPay-ссылка не умеет отменять перевод.
Условие «новый клиент» проверяется при расчёте и создании счёта; ранее выданные счета с согласованной ценой сохраняются.

Локальные HTTP/SQL-тесты: `python -m unittest scripts.test_first_payment_promo_unit scripts.test_payment_unit scripts.test_prepaid_checkout_unit`.
Они используют SQLite in-memory, поддельную локальную подпись уведомления, mock почты и OS-адаптера VPN;
реальных переводов, внешней почты, WG/DNAT нет. Продакшен-smoke — только preview/check с откатом внешней транзакции.

## Персональная цена на карточках клиентов

Android, PC (один renderer для Windows/macOS/Linux), iOS, OpenWrt и Keenetic берут цену карточки
из `profile.payment_previews[plan_id].amount` только при непустом серверном `promo_code` и свежем `calculated_at` (не старше 5 минут).
Без кода, с устаревшей/невалидной суммой или после оплаты возвращается обычная цена; общий `/payments/plans` не изменяется.
Цены форматируются с копейками, без локального умножения на процент. После `/promo/check` клиенты перечитывают профиль,
старые запросы не должны переносить персональную цену между аккаунтами. Внешний вид карточек и TV-focus не меняется.

Проверки: Android `PromotionalPriceTest`, PC `test/promoPricing.test.mjs`, роутеры `scripts/test-promo-pricing.mjs`.
На macOS: из `ios/` запустить `swiftc -parse-as-library Silent/Models/Models.swift scripts/test-promo-pricing.swift -o /tmp/silent-promo-pricing && /tmp/silent-promo-pricing`.
Новые клиентские исходники требуют пересборки соответствующих приложений/пакетов; обновление backend само не заменяет установленные клиенты.
