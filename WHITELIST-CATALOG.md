# Автообновление серверного каталога белых списков

## Что работает

Фоновый `whitelist_sources` запускается существующим лидером backend через 90 секунд после старта API. Он читает фиксированные HTTPS-источники каждые шесть часов. При ошибке повторяет попытку через 15 минут. Отдельный файловый lock защищает от параллельного запуска CLI и агента.

Источники:

- https://github.com/hxehex/russia-mobile-internet-whitelist — отдельные имена из `whitelist.txt`; каталог консервативно сохраняет их как exact, не добавляет поддомены.
- https://github.com/jinndi/geosite-cheburnet — JSON ruleset с сохранением различия `domain` и `domain_suffix`.

Код проектов не заимствуется. Наличие записи — только `source_listed`, не измеренная доступность. Отдельные источники могут зависеть друг от друга; два совпадения не означают два независимых измерения.

## Границы автоматизации

Этот этап реализует выбранный владельцем вариант **только серверные источники**. Проверок телефонов, SIM, истории посещений и клиентской телеметрии нет. Проверка с зарубежного VPS не доказывает, что ресурс доступен во время ограничений на российском операторе. Опрос раз в шесть часов не делает старые исходные измерения свежими: `last_success_at` — время успешного скачивания, `content_observed_changed_at` — время обнаружения изменения байтов, `upstream_updated_at` неизвестно.

**Действующая `/api/vpn/routing-policy` без profile не изменяется.** Каталог не вызывает `save_policy`, не добавляет общий DIRECT, не снимает VPN overrides. `auto_publish=false` и `reachability=not_measured` — явная граница, не обещание автоматического определения операторской доступности. Обычные клиенты и OpenWrt новых правил из каталога не получают. По отдельному согласованию добавлена изолированная Android-сборка с opt-in профилем и поддержкой exact-правил (см. раздел клиентского теста).

## Защита обновлений

- Только два фиксированных URL; произвольные адреса, прокси окружения и HTTP redirects не используются.
- Ограничены время скачивания, размер файла и количество записей. HTML, пустой источник, неизвестные условные правила JSON не принимаются.
- Общие TLD, ряд общих CDN/облачных суффиксов и некорректные значения попадают в карантин. Это защитный список, не полный реестр публичных суффиксов; кандидаты по-прежнему требуют проверки.
- IP/CIDR и VPN-подписки не преобразуются в домены. Секреты из строк подписок в карантин не сохраняются.
- Скачивание с ETag/304 сохраняет содержимое без изменения revision. Сбой одного источника не стирает его последний корректный набор; статус становится stale.
- Изменение более половины набора при наличии минимум 20 старых записей удерживается как `ExcessiveSourceChange`. Администратор должен проверить источник; автоматического обхода предохранителя нет.
- JSON заменяется атомарно. Предыдущие содержательные версии сохраняются в `history/`, максимум восемь. Каталог не управляет firewall, DNAT, WG peers или WDTT.

## Проверка

В каталоге backend:

```sh
python scripts/test_whitelist_catalog_unit.py
python -m ai.whitelist_sources --once
python -m ai.whitelist_sources --status
```

Состояние хранится в `update/whitelist-discovery/catalog.json`. Административный GET `/api/admin/settings/routing-policy/sources` возвращает размеры, revision, свежесть и ошибки источников; действующий admin authentication обязателен. Полные typed-записи и карантин находятся в JSON каталога.

При необходимости отключения убрать агент из списка фоновых задач и выполнить штатный deploy; active policy при этом остаётся прежней. Для возврата содержимого каталога можно атомарно восстановить проверенный файл из `history/` при остановленном сборщике. Не подменять этим файлом manifest действующей routing policy.
## Изолированный клиентский тест

GET `/api/vpn/routing-policy?profile=catalog-test` читает текущий каталог, не вызывает `save_policy` и не меняет дефолтный ответ.
Только специальная Android debug-сборка `com.silent.vpn.catalogtest` запрашивает этот профиль.
`direct_exact_domains` сохраняет exact-семантику источников, `direct_domains` объединяет suffix источников и явные DIRECT-домены действующей политики backend. Общие зоны `ru`, `su`, `xn--p1ai` из старой политики в тестовый профиль не переносятся: иначе все российские сайты обходили бы VPN независимо от каталога. Ручное добавление `sweb.ru`, например, применяется также к его поддоменам.
`vpn_domains` наследует действующие override и имеет приоритет на клиенте даже при совпадении с DIRECT. Изменения в обычном редакторе routing-policy backend автоматически учитываются при следующем запросе тестового профиля (клиент обновляет список раз в 5 минут). Удаление ручного DIRECT не удаляет запись источника; чтобы принудительно оставить такой домен в VPN, добавить его в VPN-список.
Неизвестный profile даёт 400, недоступный/слишком большой каталог — 503 (клиент сохраняет last-good).
Каждый список ограничен 2000 правилами, ответ — 240000 байтами; revision учитывает оба типа и VPN-override.
Обновление кандидатов на сервере остаётся раз в 6 часов; проверенная доступность оператора не заявляется.
Порядок сборки/приёмки: `android/CATALOG-TEST.md` в корне проекта.
