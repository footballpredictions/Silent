# Android: регрессия восстановления после a54004c

## Что подтверждено

Пользователь проверял Silent VPN (debug) на Vivo V2520A: после потери сигнала трафик зависал до ручного выключения/включения, одновременно возникали лишние переподключения без движения. SHA256 установленного APK совпал с выданной сборкой a54004c. Существование процесса и число воркеров не доказывают передачу пакетов.

1. Реальный `SilentVpnService` с живым транспортом получил только `validated_after_gap` и послал ему STOP. Исходный device test: `expected:<0> but was:<1>`. Android VALIDATED отражает системную проверку сети и сам по себе не подтверждает обрыв VPN. Мой a54004c ошибочно усилил этот сигнал до обязательного рестарта и дополнительно пересоздавал WireGuard/TUN.
2. Сетевую реализацию a54004c сначала откатили локально к f7e94c4, сохранив независимые исправления плитки. На этом основании обратный тест подтвердил старый дефект: `wifi_gap_restored` оставлял прежние сокеты, поскольку процесс был жив. Это также объясняет слепую зону прежних watchdog: свежая статистика и положительные воркеры могут сохраняться при зависшем канале.
3. На исходном APK разрешённое отключение данных Vivo на 10 секунд породило два восстановления одного обрыва: 11:03:43 `cell_gap_restored`, затем 11:03:45 `internet_restored`; внешний транспорт и site-router сменились. В этом конкретном опыте туннель всё-таки вернулся, поэтому его нельзя называть воспроизведением всех зависаний между вышками.

4. В 11:29:43 live-журнал поймал независимый разрыв на месте: фоновый `Site bypass: 34 hole(s)` пересоздал site-router 9695→15044 при неизменном WDTT 10978 и без network recovery. Настоящий native/TUN device test подтвердил RED: изменение только списка DNS-адресов завершило прежний WG-процесс (exit143). Этот путь существовал в браузерной маршрутизации до a54004c.

## Исправление

- `onLosing` больше не объявляет blackout. События IP/VALIDATED относятся к выбранной underlying-сети; при исключённом приложении предпочтение получает её реальный default. Служебные сети без INTERNET не выбираются.
- Подтверждённая потеря сети, смена Network/IP/транспорта и подтверждённый отказ данных перезапускают WDTT. Один VALIDATED и короткое мигание флагов не останавливают живой транспорт.
- Очередь объединяет причины и сохраняет сильную; выполнение последовательно. Обработанное восстановление того же Network защищено от повтора, отложенный start проверяет владельца сессии внутри mutex, shutdown отменяет его.
- Удалено принудительное пересоздание WireGuard при каждом восстановлении. Его peer — loopback; внешний транспорт можно заменить с сохранением TUN/WG и соединений приложений. Изменения настоящей конфигурации по-прежнему применяются обычным путём.
- Native site-router считает только исходящие plaintext-пакеты приложений, реально отправленные в VPN, и входящие расшифрованные пакеты. DIRECT и исходящие внутренние OTA/probe-пакеты не создают спрос на восстановление. Локальный `/_silent/health` не вызывает сеть и не содержит адресов/ключей.
- Если исходящие пакеты остаются без ответов 12 секунд, сервис выполняет две ограниченные проверки через существующий зашифрованный WG. Любой upstream HTTP-ответ, включая 4xx/5xx, или входящий пакет отменяет подозрение. Локальный proxy error не считается upstream-ответом. После двух отказов выполняется WDTT-only recovery. Повтор проверки ограничен минутой и требует новых пакетов приложений. Простой не создаёт радио-проверок или рестартов; постоянный CPU lock не добавлен.
- Исправления состояния/клика/последнего отложенного обновления плитки и captcha сохранены.

- Сетевые callbacks и очередь выполняются последовательно на Main; epoch отбрасывает callbacks предыдущей сессии; повторный CONNECT заново регистрирует callback. Это дополнительно закреплено настоящим device RED→GREEN при повторной setup сессии.
- Обновление только DNS-адресов обхода больше не пересоздаёт WG/TUN. BrowserScopedTunnel сравнивает фактическую конфигурацию устройства отдельно от списка адресов, передаёт адреса по private stdin и ждёт подтверждения native. Список меняется под mutex; learned DNS и решения существующих потоков сохраняются. Настоящие изменения WG/Android-конфигурации по-прежнему применяются обычным путём.

## Проверки

JDK Android Studio JBR, из `android/app`:

```powershell
.\gradlew.bat assembleDebug assembleDebugAndroidTest testDebugUnitTest --console=plain
```

331 JVM tests, 0 failures; production tile harness `python scripts/test_tile_state_harness.py`: 18 PASS.

Изолированный Android x86/API28 emulator, без аккаунта и реального VPN пользователя:

```text
adb -s emulator-5584 shell am instrument -w -r -e class com.silent.vpn.service.BrowserPolicyRefreshDeviceTest,com.silent.vpn.service.ServiceRecoveryRegressionDeviceTest,com.silent.vpn.service.TunnelPowerDeviceTest,com.silent.vpn.network.NetworkRecoveryDeviceTest com.silent.vpn.debug.test/com.silent.vpn.HiltTestRunner
```

Финал: `OK (12 tests)`. Проверяются настоящий service → manager STOP, отсутствие STOP от VALIDATED, приоритет обрыва в очереди, невидимый Android зависший канал, upstream HTTP error, отмена старта после stop и настоящий ограниченный CPU lock. В промежуточном прогоне таймаут очереди 4 секунды был короче предусмотренного ожидания cellular на Wi-Fi эмулятора; fixture исправлен на Wi-Fi, механизм ожидания продукта не менялся.

Go tests собраны NDK для Android x86 и выполнены на том же эмуляторе: 11 PASS. В `TestOTAOverExistingEncryptedWireGuardKeepsApplicationTCP` настоящий WG теряет исходящие UDP-пакеты при сохранении процесса/интерфейса: запрос перестаёт проходить, plaintext TX растёт без RX; после снятия потери исходный WG снова передаёт данные. Проверено, что OTA не увеличивает счётчик исходящих пакетов приложений.

Обновление адресов отдельно проверено настоящим процессом site-router: PID/TUN сохраняются после ACK. В native encrypted-WG тесте при обновлении адресов сохраняется та же открытая TCP-сессия приложения.

## Проверка на Vivo

На первой промежуточной сборке 2afd37af по отдельному разрешению установлен исправленный debug APK поверх прежнего, без очистки данных. VPN снова запущен из сохранённой конфигурации. В 11:23:16–11:23:26 MSK мобильные данные отключены и возвращены в `finally`; Wi-Fi был выключен.

11:23:28 — одно `cell_gap_restored`. WDTT PID 9615 → 10978; site-router PID 9695 сохранился. После восстановления запрос через localhost OTA и существующий encrypted WG получил upstream HTTP422 с `X-Silent-Upstream: 1`; повторная проверка заняла 0,171 секунды. HTTP422 ожидаем для диагностического запроса без обязательных параметров и подтверждает доставку до API, а не ошибку транспорта. Ручное переключение VPN после обрыва не понадобилось.

До 11:26 MSK процесс транспорта сохранился без повторного восстановления. Это подтверждает контролируемую потерю мобильных данных и устранение двух воспроизведённых ошибок. Настоящий переход между движущимися вышками и все сочетания Wi-Fi/оператора в этой проверке не воспроизводились.

Финальный APK32223262 успешно установлен на Vivo, его SHA сверена повторным adb pull. Владелец включил VPN вручную: повторный запуск интерфейса через ADB отклонила автоматическая проверка инструментов (blocked by policy); ограничение не обходили. Контроль именно финальной сборки: data-off11:46:10–11:46:20 MSK, в11:46:21 одно cell_gap_restored, WDTT22946→24046, site-router23065 сохранился. Upstream ответ через существующий WG получен за0.338с с X-Silent-Upstream:1, ручной off/on после обрыва не понадобился.
